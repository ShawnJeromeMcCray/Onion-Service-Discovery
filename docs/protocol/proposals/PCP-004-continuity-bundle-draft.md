# PCP-004: service history bundle

State: OWNER-APPROVED FOR DRAFT AND IMPLEMENTATION (2026-10-14) / NEEDS INDEPENDENT REVIEW.
Decision: owner answer "Entwurf + Umsetzung" (see the decision register). This is
an additive protocol v1 extension; it changes no existing record or byte format.

## Problem

A Node fetches only the current Manifest from
`/.well-known/onion-service-discovery.json`. It can connect that Manifest to a
logical identity only if it already holds every earlier revision and every key
rotation or Onion migration proof. Without them the Manifest is an orphan and the
direct check ends in `HISTORY_INCOMPLETE`. In practice:

- a Node that first meets a Service after any revision (revision 2 or later)
  cannot admit it at all;
- after a key rotation or Onion migration, every Node that has not received the
  proof by other means stops at the previous state.

## Exact format

`GET /.well-known/onion-service-discovery-history.json` on the Service's own
Onion, beside the Manifest. Same transport rules as the Manifest: Tor only, no
redirects, HTTP 200, `application/json` (optional UTF-8 charset), identity
encoding, at most **1,048,576 bytes**.

```json
{"protocol":"Onion Service Discovery","protocol_version":1,"bundle_type":"service_history","records":[ ... ]}
```

- Exactly these four members; strict duplicate-rejecting JSON.
- `records`: 1 to **256** distinct signed records, each a complete
  `service_manifest`, `service_identity_key_rotation` or `onion_service_migration`
  record that verifies on its own (schema and signature). Order carries no
  meaning; publishers write the history in chronological order.
- The bundle itself is unsigned and has no authority. It can only supply
  records whose own signatures already prove what they claim.

## Verification

Given the bundle bytes, the current Manifest fetched from the same Onion and
verified with exact Onion binding, and the records the verifier already holds:

1. Bytes over the limit are `HISTORY_BUNDLE_INVALID`. Strict JSON errors
   (invalid JSON, duplicate members, a non-object root, more than 256 array
   elements) propagate unchanged. Wrong members, values or an empty record list
   are `HISTORY_BUNDLE_INVALID`.
2. In array order, each entry must be an object, must verify as a record (its
   errors propagate unchanged), must have one of the three allowed types and must
   not repeat an earlier entry's content hash; otherwise `HISTORY_BUNDLE_INVALID`.
3. Derive identities over the union of known records, bundle records and the
   current Manifest (at most 10,000 records).
4. Find the identity whose history contains the current Manifest's hash:
   - none: state `INCOMPLETE`, nothing is admitted;
   - `FORKED`: state `FORKED`;
   - `VALID` with that Manifest as current state: `CONNECTED`;
   - `VALID` with a newer known current state: `DOWNGRADE`.
5. `admitted_hashes` (sorted): bundle records that belong to that identity
   (history, rotation, migration, revision-conflict and transition-conflict
   hashes), excluding the current Manifest and records already known. Unrelated
   identities in a bundle are ignored.

A Node fetches the bundle only when a direct check would otherwise end in
`HISTORY_INCOMPLETE`, at most once per check, stores only `admitted_hashes`, and
then repeats its ordinary continuity derivation. `FORKED` records stay as fork
evidence; a bundle can never hide or resolve a fork, and it never replaces a pin.

## Publishing

`manifest:install` maintains the bundle automatically from genesis: each
installation appends the previous Manifest, the supplied rotation or migration
proof and the new Manifest, and writes the file only when the result connects
to the installed Manifest. Existing installations rebuild it once with
`history:install WEBROOT SIGNED_RECORD...`. The front controller serves the file;
static hosting can serve it unchanged.

## Vectors and limits

`protocol/test-vectors/service-history.json` (generated by
`tools/generate_history_vectors.py` from the signed identity-sequence fixtures)
holds the shared positive and negative cases for PHP, TypeScript and Python:
first contact after revisions, rotation, migration, combined transition, missing
proof, fork evidence, unrelated records, downgrade, malformed bundles, foreign
record types, tampered signatures and Onion-binding mismatch.

## Review questions

The suffix `onion-service-discovery-history.json` is a second well-known name to
register beside the Manifest's (see the registration preparation). Independent
review should confirm the limits and that serving complete public history adds
no information beyond what the published revisions already disclosed.
