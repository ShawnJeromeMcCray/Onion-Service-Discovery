ONION SERVICE DISCOVERY
RECORD LIFECYCLE MATRIX AND PROTOCOL ARCHAEOLOGY STANDARD


1. Purpose
Every persistent or wire-level object must have a documented lifecycle. Future maintainers must be able to reconstruct why a record existed, who created it, how it was validated, when it became stale, and how a client of a specific historical version would have interpreted it.

4. Service Manifest Lifecycle
Create:
Service operator local configuration.


Sign:
Service Identity key.


Publish:
Well-Known path.


Admission:
strict size/JSON/schema/Onion binding/signature/history.


Persist:
immutable canonical content by hash plus parsed indexed fields.


Current:
selected through deterministic revision/conflict rules.


Stale:
older than accepted current revision or liveness threshold as separate axis.


Withdrawal:
new valid manifest with publish off.


Deletion:
continuity evidence long-lived; cache/raw transfer bytes may be pruned under policy.


5. Rotation Lifecycle
Created only through explicit operator rotation workflow.
Signed by old key and new confirmation if frozen protocol requires.
Never generated by peer.
Accepted atomically with continuity transition.
Conflicting rotation retained as fork/conflict evidence.


6. Migration Lifecycle
Created by Service operator.
Signed by current Service Identity.
May accumulate old/new endpoint confirmation observations.
Historical binding retained.
Current Onion updates only after valid migration semantics.


7. Node Descriptor Lifecycle
Created by Node operator/software.
Signed Node Identity.
Revision/equivocation handling.
Peer learned from descriptor remains source candidate until policy admits.


8. Direct Observation Lifecycle
Created by observing Node after local Direct Verification.
Signed Node Identity.
Imported copies remain attributed to original Node.
Observation ages; underlying Manifest signature/history remains separately evaluated.


9. Peer Assertion Lifecycle
Created/relayed by peer context.
Never upgraded to local Direct Observation without local verification.
Aggressive finite retention acceptable.


10. Candidate Lifecycle
Created from bounded source event.
Minimal data.
Transitions through explicit state machine.
Eventually verified, backoff, rejected or quarantined.
Expired transient source evidence can be pruned.


11. Moderation Lifecycle
Issued by selected moderation source.
Signed/provenance.
Expires/revokes according to source semantics.
Never mutates identity validity.


12. Snapshot Lifecycle
Built from deterministic current export state.
Signed descriptor.
Immutable chunks.
Expires as synchronization convenience, not as Service identity evidence.


13. Pin Lifecycle
Created by explicit user action.
Local/private.
Never peer-controlled.
Survives cache rebuild.
Deleted only explicit user action/full reset.


14. Archaeology Requirement
Given:
software version
protocol version
schema version
dataset/record set
configuration
the project should be able to reproduce or explain the historical semantic outcome.


15. Version Metadata
Release manifest records:
software version
supported Protocol versions
DB schema
client storage schema
Unicode/confusable data version
search ranking version
limits registry version
conformance suite version.


16. Decision Snapshot
Each release archives:
accepted ADR index
Protocol proposals
Security exceptions
seed list
permission inventory
external-standard baseline.


17. Semantic Version Pinning
When behavior can change without wire change, assign explicit local semantic version:
ranking algorithm version
confusable detection version
moderation format version
source-selection policy version
where needed for reproducibility.


18. Old Record Reader
Reference tooling SHOULD provide:
protocol:inspect <record>
with option to specify/auto-detect Protocol version and explain:
schema
signature
revision state
known deprecations.


19. Migration Preservation
DB migration must not erase original Protocol record version/hash needed for forensic reconstruction.


20. Client Storage Migration
Where a derived current view changes due software logic:
migration test documents old expected interpretation and new interpretation.
Do not silently rewrite user pins/history.


21. Protocol Version Archive
Repository retains:
all stable schemas
test vectors
registries
RFC-style spec
conformance suite manifests
for supported and EOL Protocol versions.


22. Software Release Archive
Release evidence keeps:
source revision
artifact hashes
SBOM
provenance
config schema
DB migrations
known limitations.


23. Deprecation Metadata
When record/capability deprecated:
introduced
deprecated
last supported
replacement
security reason if applicable.


24. Historical Test
Maintain at least one fixture from every stable software release generation and run current migration/inspection tools against it.


25. Forensic Questions
Tooling/docs should answer:
Why did client show this Service as migrated?
Which key authorized rotation?
Which exact Manifest hash was current?
Which Node supplied an observation?
Was evidence direct or peer-reported?
Which policy marked it stale?
Which version of ranking/confusable logic applied?


26. Audit Trail Without Surveillance
Archaeology uses Protocol/release metadata, not user search logs.
No requirement to persist user behavior.


27. Record Tombstones
If local transient data deleted, tombstone only if needed for sync semantics.
Do not create indefinite tracking metadata without purpose.


28. Schema Evolution
Every field:
introduced version
required/optional
default/absence semantics
removal strategy.
Never recycle old field name with different meaning.


29. Error Code Evolution
Registry retains deprecated codes and version ranges.
Do not assign old code to new meaning.


30. Capability Evolution
Same token never changes incompatible semantics.
New semantics -> new token/version.


31. Seed History
Release archive records built-in seed set.
Useful to reconstruct bootstrap behavior, not trust truth.


32. Permission History
Extension release archive records manifest permissions.
Allows reviewers to detect historical privilege expansion.


33. External Standards History
Record which RFC/JSON Schema/WCAG/Tor/PHP baseline was checked for each release.
Future changes can be compared.


34. Reproduction Bundle
For significant incident/audit:
input records
software container/toolchain or documented environment
configuration redacted
expected result
actual result.


35. Protocol Archaeology CI
Run:
old stable golden corpus through matching historical interpreter where available;
current migration path against old DB/client fixtures;
ensure archived schemas/vectors remain readable.
